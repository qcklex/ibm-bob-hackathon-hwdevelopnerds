The Problem: Line Coverage Lies

A Java utility library ships with a 95% line-coverage score — green across the board. Most teams would stop here. But line coverage only proves a line was executed, not that any assertion caught a wrong result.

Running PIT mutation testing reveals the real picture: PIT makes tiny logic changes — flips a conditional, removes a return value, inverts a boundary — then checks whether any test fails. 82% of mutants were killed. 18% slipped through.

The gap: 95% line coverage  ·  82% mutation score.

The Approach: Automated Kill Loop

Each round is driven by a single shell command. IBM Bob's mutation-climb skill runs the loop autonomously: it reads surviving mutants, decides which tests to write, writes them, then re-runs PIT to verify the kill.

1
Run PIT via sh run_round.sh Compiles the project, executes mutation analysis, writes raw XML to pit-output.txt
2
Parse survivors report.py converts mutations.xml into survivors.md and appends a row to rounds.csv
3
Bob reads survivors and writes targeted tests Each surviving mutant is a concrete, precise test target — boundary assertion, missing overload call, or time-advance test
4
Repeat until score plateaus or target is reached Goal: mutation score ≥ 90%. Every round, survivors.md shrinks and chart.png updates.
Why this works:
Line coverage gives no direction — every uncovered mutant looks the same. Mutation survivors give exact coordinates: file, line, mutation type. Bob converts each coordinate into one focused test assertion.

How IBM Bob Is Used

Three Bob capabilities work together to make the loop autonomous: a domain skill, a custom mode, and parallel subagents.

Skill

mutation-climb

A Bob skill stored at .bob/skills/mutation-climb/SKILL.md. It contains the full loop protocol: how to invoke PIT, how to parse survivors.md, how to rank mutants by kill probability, and how to write focused JUnit 5 tests that target one mutation type at a time.

Activated with /mutation-climb at the start of a session — Bob then drives every round without further instruction.

/mutation-climb
Custom Mode

Test Engineer mode

A lean Bob mode that restricts the tool palette to exactly what mutation testing needs: file read/write, symbol search, grep, and the Maven test runner. Removing irrelevant tools keeps Bob focused and prevents accidental edits outside src/test/java/.

The mode also sets a role definition that primes Bob to reason about assertion strength, branch coverage, and boundary conditions rather than feature implementation.

mode: test-engineer
Subagents

Parallel survivor analysis

When a round produces a large survivor list, Bob spawns independent subagents — one per class under test (MoneyUtils, Validators, SimpleCache, etc.). Each subagent reads its class, reads the survivors assigned to it, and returns a batch of test methods.

The parent agent merges the results and writes a single coherent test file per class, then triggers the next PIT run.

What Is Next

The loop proved the concept on a small utility library. The following steps scale it to real-world projects and make the skill generally reusable.

Push mutation score to ≥ 95%

The remaining 12 survivors cluster in time-sensitive and overloaded methods. The next rounds will introduce clock-injection helpers and parameterised tests to kill the residual boundary mutations.

Publish mutation-climb as a shared Bob skill

Package the skill with a generic run_round.sh template so any Java Maven project can adopt the loop in under ten minutes — no bespoke scripting required.

Extend to other languages

The skill protocol is language-agnostic at the Bob layer. Port the PIT-specific shell commands to equivalents for Python (mutmut), JavaScript (Stryker), and Go (go-mutesting) to broaden applicability.

CI integration

Add a GitHub Actions workflow that runs PIT on every pull request, posts the mutation score as a PR check, and blocks merge if the score drops below the configured threshold.

Survivor-based PR review mode

Train a Bob custom mode that reads the diff of an incoming PR and cross-references it against known surviving mutant patterns — flagging likely weak assertions before the code lands.

Benchmark Bob models on test quality

Use the reproducible rounds.csv metric as a cross-model benchmark: run the same survivor list through different LLMs and measure how many mutants each model kills per round to guide model selection.
